# 智能采集质量管控平台

面向数据采集团队的质量管控与效率优化平台。覆盖采集任务编排、抓取结果校验、采集链路监控、数据格式转换、去重比对、异常重试、采集审计与合规管理的完整采集质控链路。

这是一个前后端分离的管理平台：前端 Vue 3 + Vite + TypeScript，后端 FastAPI（Python）。
两边各自独立启动，前端 dev server 已关掉自动打开页面，启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/              统一请求封装
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false）
├── backend/                  FastAPI（Python） 后端
│   ├── app/routers/          每个业务模块一组接口
│   ├── app/services/         业务规则与状态流转
│   └── app/store.py          内存数据仓库与示例数据
├── .gitignore
└── docker-compose.yml
```

## 启动

### 后端

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
./run.sh
```

健康检查：`curl http://127.0.0.1:8000/api/health`

### 前端

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，
需要自己访问。`/api` 由 vite 代理到后端 `http://127.0.0.1:8000`。

### 测试

```bash
cd backend
.venv/bin/python -m pytest tests -q
```

## 采集请求排队调度

多个采集计划共用同一目标站点时，请求名额按频率策略统一分配，流程如下：

1. **提交请求**：`POST /api/taskplan/{id}/queue/submissions`，计划进入所属策略的等待队列。
   同一计划（或同一 `request_key`）重复提交只保留一个排队位置，重复提交返回原位置并标记 `duplicate: true`。
2. **推进轮次**：`POST /api/throttle/queue/rounds` 或 `POST /api/throttle/{id}/queue/rounds`。
   每轮先推进生命周期（运行中到期进入释放中、释放中到期收口），再按额度与并发分配新名额。
3. **观察排队**：`GET /api/throttle/queue` 查看各策略看板（本轮已消费额度、运行中、等待顺序、
   被降级计划、预计释放时间）；`GET /api/throttle/queue/waiting` 是跨策略的待等待清单；
   `GET /api/taskplan/queue/waiting` 把等待视图补进采集计划清单。
4. **流转记录**：`POST /api/throttle/queue/records/{id}/actions`，支持开始请求、释放请求、收口请求、
   恢复排队、切换优先级；已收口记录不能回到任何活动阶段。

### 排队规则与冲突判定

判定冲突时按以下顺序取第一条：

- **日请求上限**是硬约束：额度耗尽后无论优先级多高都不再分配名额，等待原因给出"日请求上限已耗尽"，
  预计释放时间为次日额度重置时间。
- **稳定优先级**：额度内按 `计划优先级 × 策略优先级权重` 排序，同分按提交时间、排队记录编号排序，
  同一份数据每次调度结果一致。策略的「排队策略」还支持先进先出、轮转两种口径。
- **公平性兜底**：等待轮数会带来有限补偿；计划连续占用达到「连续占用上限」后，
  只要还有别的计划在等就必须让出一轮，并记录到「被降级的计划」与记录的降级原因里。
- **唯一占用**：检查额度、占名额、写记录在同一把进程级可重入锁里完成，
  两个轮次同时争抢最后一个名额时只接受唯一占用，另一个返回可读的失败原因。

### 生命周期

排队记录固定按 `等待中 → 运行中 → 释放中 → 已收口` 流转，只允许向前。
已收口是终态：切换优先级只更新当前活动记录；恢复排队会新建一条等待记录
（带 `恢复自` 指向旧记录），旧记录保持已收口，保证轮次历史可追溯。

### 关联模块

- **采集计划**：清单补入 `排队状态`、`排队位置`、`预计释放时间`、`等待轮数`、`待办`，
  计划待办随轮次自动刷新；`GET /api/taskplan/pending` 返回等待/运行/释放中的待办。
- **告警中心**：等待超过「等待超时轮数」或「等待超时秒数」时生成一次排队超时提醒，
  `GET /api/alert/queue` 查看，`确认提醒` 动作确认后进入 `已确认`；同一等待记录不会重复提醒。

## 约定

- 每个模块的前端页面在 `frontend/src/views/<模块>/index.vue`，后端接口在
  `backend/app/routers/<模块>.py`，业务规则在 `backend/app/services/<模块>.py`。
- 列表接口统一返回 `{ items, total, page, size }`，动作接口统一返回 `{ ok, message }`。
- 状态流转只允许在 `app/services` 里改，路由层不做业务判断。
